IMPLEMENTATION REFERENCE

How search and counting work

AI helps express your topic as keywords. Local code then finds matching papers and computes the charts; the model never invents counts or judges individual papers.

Keyword (default): comma-separated phrases → local matching → charts.
AI: description → AI concepts → your review → hybrid matching → charts.
Every matching publication contributes to the count.

1. Build the conference corpus

The collector downloads the official NeurIPS, ICML and ICLR event catalogs and, when needed, separate abstract feeds. It follows pagination and verifies the declared event count and unique event IDs. Raw responses, fetch dates and content hashes are cached locally.

  • One unit is a conference/year publication, not a unique algorithm or an arXiv upload.
  • Oral, poster and spotlight presentations are deduplicated within a conference-year: OpenReview ID first, research submission ID when available, then normalized title fallback. Poster metadata is processed first. Title aliases can reconcile presentations; conflicting tracks cause an error rather than a silent merge.
  • Main research-track papers are selected by default. Search scope can add position papers and datasets-and-benchmarks papers. Workshops and arXiv-only papers are not covered; other catalog tracks are retained separately.
  • Search reads titles and abstracts, not full PDFs. Each prompt searches the cached snapshot, rather than crawling the web again.

2. Normalize text and build an index

  1. Apply Unicode NFKC normalization, lowercase text, and normalize dash variants and whitespace.
  2. Extract English alphanumeric tokens using [a-z0-9]+. Punctuation and hyphens become token boundaries.
  3. Remove a final s from tokens longer than four characters, except words ending in ss, us or is. For example, models → model. This is a heuristic, not a linguistic lemmatizer.
  4. Build an inverted index: each token points to the set of papers containing it. Keep normalized title-plus-abstract text for phrase checks and the title separately for ranking.

Phrase lookup intersects its token posting lists, beginning with the smallest set, then checks that the complete normalized phrase occurs contiguously with token boundaries. Thus graph neural networks can match graph neural network, but graph discovery does not match words scattered across an abstract. Up to 2,048 phrase-result sets are cached in memory.

3. Choose Keyword or AI mode

Keyword is the default. Enter up to 16 comma-separated phrases (at most 120 characters each). Every phrase must occur in the normalized title/abstract; words within a phrase must be contiguous. For example, reinforcement learning, language model requires both phrases. Empty comma segments are ignored. There is no AI call, synonym expansion, semantic matching or automatic exclusion. Keyword mode works even when server AI is disabled and does not consume the weekly AI quota.

AI mode interprets your description and offers editable concepts before hybrid search. A matching cached interpretation can be reused without a new model call. AI errors never silently switch to Keyword mode. The following steps describe AI mode.

  1. Describe the topic. Enter 3–1,500 characters. Select years, conferences and tracks in Search scope; scope filters are separate from the description sent to the model. By default, the scope covers the current year and four previous years, all three conferences and main research papers.
  2. Generate structured concepts. GPT-5.4 nano receives the description and instructions to identify essential concepts, English search phrases, optional supporting groups and suggested exclusions. The AI selects exclusions from the intended scope, including explicit requests and inferred out-of-scope concepts, and explains its choices. There is no hard-coded exclusion list. Before review, a deterministic recall safeguard expands common RL/LM terms and treats autoregressive evidence as optional; AI exclusions and their explanation are preserved. Raw AI concepts and adjustments are retained in exports. It is instructed to omit conversational wording and background motivation, preserve distinctions such as discrete versus continuous diffusion, and request clarification when the intent cannot be represented faithfully.
  3. Validate the response. The request uses a strict JSON schema, and the backend validates the complete result again. Required fields are listed below. Valid structure does not guarantee correct interpretation.
  4. Review “Interpreted as”. Edit alternative phrases or exclusions, rename a label, or remove a concept. Labels describe groups; reviewed phrases drive keyword and semantic matching. Supporting groups affect rank only. More alternatives broaden lexical matching; they also change the semantic query vector. More required core groups add constraints. The effective criteria are validated again when submitted.
  5. Start the local search. Click “Search with these concepts”. If clarification is requested, revise the original description and interpret it again first. The server checks that the submitted interpretation belongs to the unchanged description.

Failure handling: refusals, authentication, billing and transport errors stop the AI request. Malformed responses or output-token truncation receive at most one retry; the output budget increases from 1,800 to 3,000 tokens. The app never extracts partial JSON or silently substitutes the old dictionary parser. If AI is disabled on the server, Keyword mode remains available.

Privacy: only the description, fixed instructions and output schema are sent to OpenAI—not the paper corpus, saved searches or scope filters. The API key stays on the server. Requests use store=false, which is not a promise of zero provider retention; your account's data-sharing settings still matter. Opening this explanation page makes no AI request.

4. Match core concepts with keywords and local embeddings

Keyword mode uses only the lexical rule: every comma-separated phrase must match. The hybrid formula below applies only to AI-mode searches. Both modes apply the identical chosen membership rule to publications and all submission outcomes for acceptance rates.

Core groups are required; alternatives within each group use OR. Supporting groups are optional evidence, not filters. For RL on autoregressive language models, the core is RL AND language models; autoregressive terminology boosts ranking but its absence never excludes a paper. Generic LLM evidence does not prove autoregressive architecture.

Keyword matching uses the full normalized title and abstract. A pinned sentence-transformers/all-MiniLM-L6-v2 encoder embeds the title plus abstract locally on CPU, truncated to 256 wordpieces, using masked mean pooling and L2 normalization. Vectors are cached by document content, model revision, precision and preprocessing. No paper text is sent to OpenAI. Core-query embeddings are built from the reviewed alternatives, not stale text in the original prompt.

Lᵢ(p) = any core-i keyword occurs in title/abstract
Sᵢ(p) = cosine similarity to core-i alternatives
Q(p) = cosine similarity to all core alternatives together
match(p) = ALL Lᵢ(p) OR [Q(p) ≥ 0.45 AND ALL (Lᵢ(p) OR Sᵢ(p) ≥ 0.30)]

Reviewed exclusions and year/venue/track filters are applied afterward. AI-proposed exclusions appear in the editable exclusion box; no topic is automatically excluded by application code. Exclusions remove any title/abstract mention, including background comparisons, so review the AI's choices and remove overly broad phrases. They apply to both keyword and semantic matches, including the topic acceptance-rate pool. Supporting terms do not enter this predicate. Thresholds are experimental, not validated relevance probabilities; both false positives and false negatives remain possible. Every document is evaluated—there is no top-k cutoff for the charts. If embeddings are unavailable, a new hybrid search fails visibly rather than silently changing to keywords.

There is no search-history feature. The legacy local keyword API remains available without AI or embeddings; its lexical rules are preserved.

5. Count all matches by conference year

C(y, v) = number of matching publications in year y and venue v
C(y) = sum of C(y, v) across selected available venues
Rate(y, v) = 1,000 × C(y, v) / papers searched in that year and venue
  • Every matching publication contributes one, regardless of how many phrases it matches. The 20-paper display page does not limit the chart or export count.
  • Bars are stacked by conference, using the conference year—not the first arXiv upload date.
  • A publication can match several topics. Distinct conference/year publications are not deduplicated across venues; counts are not numbers of novel algorithms.
  • Complete coverage means catalog reconciliation and selected-track metadata checks passed. Missing abstracts or unresolved in-scope events make coverage partial.
  • Unavailable/failed sources have missing counts, not zero. Partial years are hatched and starred; totals include available papers only. If every selected source in a year is unavailable, the chart displays NA.
  • Counts are automatic. There is no approval, confirmation, Include/Exclude vote or reviewer-dependent adjustment.

6. Combine rankings without changing counts

Keyword mode ranks by phrase evidence, favoring distinctive phrases and title matches. AI mode additionally uses optional supporting evidence and a second ranking from cosine similarity to the core query. For AI mode, reciprocal rank fusion combines both complete candidate rankings:

score(p) = 1 / (60 + keyword rank) + 1 / (60 + semantic rank)
+ 0.001 × min(number of matching supporting groups, 4)

Each supporting group contributes once, not once per synonym. Rank ties are resolved by paper ID; final score ties prefer newer years then ID. Supporting evidence is lexical and is never an architecture classifier. Scores and cosine similarities are not probabilities. Ranking and pagination never change candidate counts. The JSON export records the exact policy, thresholds, model revision, core/supporting evidence and whether a match required semantic expansion.

An abstract containing “policy optimization”, “rectified flow” and “text-to-image” satisfies all three groups and is counted once in its conference/year. A paper containing only “flow matching” and “image generation” does not satisfy the RL keyword group; it would need sufficient semantic evidence for the RL core as well as the whole query to qualify. Two RL synonyms do not count twice.

Matching terminology does not prove the paper's main contribution: all three phrases could occur in background discussion. Removing the image-generation group would also admit matching work outside image generation.

8. What these numbers mean

  • These are automatic hybrid candidate counts, not verified semantic relevance or an exhaustive field-size measurement. AI interprets the question; local embeddings compare text similarity, not the truth of each paper’s claimed topic. Full-paper relevance is not verified.
  • The model can omit a key concept, add an unnecessary requirement, choose overly broad alternatives, or ask an unnecessary clarification question. Strict JSON does not prevent these semantic errors. Review the effective phrases, not just their labels.
  • False positives include background comparisons, a language model used only as a judge, or continuous-time discrete-state models mistaken for continuous-state models. Broad alternatives such as “image generation” do not by themselves establish use of flow matching.
  • False negatives include unfamiliar synonyms, concepts absent from abstracts, plural-normalization edge cases, too many required groups, or exclusions that remove background mentions. Edit the concepts or rephrase the description when results are unexpectedly narrow.
  • Only selected conferences and available catalog metadata are covered. Withdrawals and late changes can make catalogs differ from final proceedings.
  • A zero result does not prove absence of research. Growth can also reflect larger conferences; the counts CSV includes the per-1,000 denominator.

9. Cache interpretations, enforce limits and reproduce results

No saved history: the application does not persist searches or AI interpretations to disk or browser storage, and has no history menu or history API. Results are held only in bounded server memory (up to 64 results) to support the current page, pagination and downloads. They disappear when evicted or the server restarts; run the search again if a result expires. HTTP access logging is disabled. Legacy history files from older versions are not read or updated; they have not been automatically deleted.

Temporary interpretation cache: up to 64 validated AI responses are retained only in process memory, keyed by description, model and instructions. This supports concept review and avoids repeat API calls while the entry remains available. It clears on server restart. Keyword mode bypasses it. AI descriptions still reach OpenAI; this application-level policy does not control provider retention.

At the limit, the backend blocks new network attempts before contacting OpenAI. Temporarily cached interpretations and results remain usable until evicted or the server restarts. The limit applies to this installation's data root, not API calls made by other tools; deleting or changing that data root is outside its protection. The home page does not show a persistent quota banner.

Saved provenance: the JSON export records the original description, original AI interpretation, configured and returned model, prompt version, generation time, API token usage, effective edited core/supporting groups and exclusions, embedding model revision and thresholds, filters, match mode, corpus hash, snapshot date, search-rule version, matching IDs, scores and evidence. Search identity hashes effective criteria and interpretation provenance together with the corpus hash and search-rule version. Keep exported JSON when archiving a result.

Download JSON if you want to retain a result yourself. Pagination and downloads use the temporary result without reinterpreting it. Result IDs are scoped to the current server instance; they are not permanent links. The downloaded corpus and document embeddings still persist, as does the aggregate weekly AI counter, which contains only a week and request count—not queries. Acceptance rates use the currently loaded decision snapshot, as explained below.

10. Compare ICLR topic acceptance with the same-pool baseline

Topic rate = 100 × accepted matching submissions / all matching submissions
Overall rate = 100 × all accepted submissions / all submissions in the same pool
Difference (percentage points) = topic rate − same-pool overall rate

The second chart covers ICLR only: filled bars represent the searched topic, outlines represent all topics within the same submission pool. The first chart still counts publications across ICLR, ICML and NeurIPS. NA is not zero; zero matching submissions makes the topic rate undefined.

Official OpenReview public-pool snapshots: the authenticated download supplies public submissions and official Decision replies. Before enabling a year, the importer verifies exhausted pagination, API counts, file hashes, unique IDs, complete titles/abstracts, and resolved outcomes. Partial queries remain unavailable. Exhausting a public query does not prove coverage of every historical submission or agreement with the organizer’s reported cohort.

An official Decision reply takes precedence over current venue labels, including later withdrawals. If no decision is available, only an explicit withdrawn or desk-rejected status supplies the outcome. Both remain in the denominator. Unknown or conflicting decisions disable the snapshot. No Paper Copilot decision labels or accepted-publication labels are substituted.

Public-pool rates are not published conference rates. Both plotted bars use the public snapshot and are labelled accordingly. The organizer’s accepted/submitted totals differ slightly; those published rates appear separately in the details as references, not as the baseline used for the difference. This avoids comparing a topic denominator from one population with a baseline from another.

A separate, stricter import supports fully organizer-reconciled cohorts. It requires an explicit coverage audit, the identical published population definition and source, and exact reconciliation of accepted and submitted totals. Matching counts alone is insufficient proof. Such an audited cohort takes precedence over the public snapshot. Non-research or mixed-track selections remain unavailable.

The same reviewed core groups, exclusions, encoder and semantic membership thresholds are applied to all submission titles and abstracts, accepted or not. Supporting terms affect neither numerator nor denominator. If the semantic pool is unavailable or a saved policy cannot be reproduced, the topic rate is unavailable rather than replaced with a lexical rate. Topic numerators come from those submission records, not from the separate publication catalog. Keyword and embedding matching can misclassify relevance; these are descriptive estimates for the labelled pool.
